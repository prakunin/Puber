### F1 [minor] The process-wide `TabHostTelemetry.content` keeps the last tab of a previous `MainScreen`, so a new `MainScreen` is first named after that old tab
- Where: app/src/main/java/com/kino/puber/core/ui/navigation/component/NavTelemetry.kt:21-28, TabComponent.kt:111
- Problem: `TabHostTelemetry.content` is written only on `TabCommand.Open`, is never reset, and lives as long as the process. When a new `MainScreen` arrives through NewRoot, `recordNav` resolves it with the old value. The runner records NewRoot right after `puberReplaceAll`. That is before the new `MainScreen` composes and before `MainVM.onStart` sends `openTab` (MainVM.kt:51). In that gap the old tab's name goes into the nav line and into `Telemetry.screen`.
- Failure scenario: the log is on and the user is on the Bookmarks tab. They press Back at the root, which runs `appLauncher.finish()` while the process stays cached, then start the app again from the TV launcher. `LauncherVM` sends `newRootScreen(main())`, which records `nav NEW_ROOT to=Bookmarks` and sets the holder to Bookmarks. `MainUIMapper.buildViewState()` picks the default tab, so the first frames of composing `MainScreen` close as their own `frames` window labelled Bookmarks. `FrameAggregator` closes a window when the screen changes. That window holds the startup jank, which is the most useful window in the log, and it names a screen that is not on screen. Spec D3 lists this case under "must not happen". Before this round the same frames were labelled Main, which is the container but not wrong.
- Fix: bind the value to the live tab host, not to the last command. In `TabComponent`, follow `navigator.current` with `snapshotFlow` (or set the value in a `SideEffect`) and clear it in a `DisposableEffect` `onDispose` when the host leaves the composition. Add a test: a stale value, then NewRoot to a fresh `MainScreen`, gives the fallback name and not the stale tab.

### F2 [minor] Turning the log off now detaches the probes inline, so an attach that is still queued runs afterwards and leaves them attached while the log is off
- Where: app/src/main/java/com/kino/puber/core/telemetry/TelemetryRuntime.kt:68-70, 103-107 (with `plantProbes` at :100)
- Problem: `enable()` posts `attach` through `main.post`, and in production that always posts, even from the main thread. Before this round, `setEnabled(false)` also posted `detach`, so detach always ran after any queued attach. Now `flushProbesInline` runs detach at once, and `detachProbes(probesDetached = true)` posts nothing. `ActivityProbes.attach` does not check `isEnabled`. So if the off call comes before the queued attach has run, the attach runs last: `FrameProbe` tracking starts, `MemoryProbe` registers its trim callbacks and timer, and nothing detaches them. `onActivityPaused` only stops them `if (isEnabled())`. They stay attached until the log is turned on and off again. Their events are dropped, but the frame tracking and memory sampling keep running for the rest of the session.
- Failure scenario: `setEnabled(true)` and then `setEnabled(false)` on the main thread before the looper runs the posted attach. A quick double OK on the toggle while the main thread is busy rebuilding the Settings screen can do it. The result is the frame tracker and memory timer active with the log off.
- Fix: keep the inline flush and still post the idempotent detach afterwards. Drop the `probesDetached` short-circuit, so the posted detach always queues behind any pending attach. Alternatively, make `ActivityProbes.attach` return early when the sink is disabled.

### F3 [nit] The core navigation telemetry now depends on a feature screen
- Where: app/src/main/java/com/kino/puber/core/ui/navigation/component/NavTelemetry.kt:9, 28
- Problem: `core.ui.navigation` imports `ui.feature.main.component.MainScreen` to detect the tab host. That makes core depend on a feature package. Any other screen that hosts a `TabComponent` would also get the container's name.
- Failure scenario: a second tab host screen gets added, and the tab-host labelling silently does not apply to it.
- Fix: put a marker interface such as `TabHostScreen` in core and implement it on `MainScreen`, or let `TabComponent` register its host screen.
