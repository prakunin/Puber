### F1 [minor] The last frame window and open key burst are dropped when the log is switched off
- Where: app/src/main/java/com/kino/puber/core/telemetry/TelemetryRuntime.kt:66-67 (with FrameProbe.kt:40 and KeyProbe.kt:137)
- Problem: `setEnabled(false)` calls `sink.stop()` first, and that sets `isEnabled = false` at once. Only after that does `detachProbes()` post `ActivityProbes.detach` to the main thread. `detach` then closes the open window (`frameProbe.stop()` -> `aggregator.close()`) and calls `KeyProbe.detach()`, which flushes the open burst. Both emit through `Telemetry::record`, which now throws the events away because the recorder is already off. The expiry path (`onExpired`) and the storage-failure path (`onStopped`) have the same ordering. Only `onActivityPaused` flushes before the drain.
- Failure scenario: the user opens Settings, browses a few seconds, then turns the session log off. The `frames` window opened on that screen never reaches the file (up to 10 s of data per screen). Neither does a held-key burst still in progress. Every expiry also loses the last window.
- Fix: on the main thread, close the frame window and flush the key burst before `sink.stop()` (for example, post a flush and then stop). Or have the sink's stop path drain events recorded during a short grace period. The simplest change is to run `frameProbe.stop()` and `KeyProbe.flush()` synchronously in `setEnabled(false)` before `sink.stop()`, since this is called from the UI.

### F2 [minor] After the log is switched on mid-session, every frames/key/mem line has an empty `scr` until the next navigation
- Where: app/src/main/java/com/kino/puber/core/telemetry/TelemetryRuntime.kt:106; app/src/main/java/com/kino/puber/core/ui/navigation/component/NavTelemetry.kt:24; TelemetryWriter.kt:114
- Problem: `Telemetry.screen` is written only by `recordNav`, and `recordNav` returns early while the log is off. `detachProbes` also resets it to null. The new `ScreenScoped` branch in the writer uses `names.owner(event.screen)` and never falls back, so a null screen is written as `""`.
- Failure scenario: the switch is in Settings, so the user turns the log on (or off and on again) while on SettingsScreen. All `frames`, `key`, `key_lat` and `mem` lines are tagged `scr:""` until the next router or tab command. A cold start into a root screen that was set without a router command looks the same.
- Fix: seed `Telemetry.screen` from the current top screen when the probes attach (the navigator top or a last-known value kept while the log is off). Alternatively, have the writer fall back to `lastScr` when a `ScreenScoped` event's screen is null.

### F3 [minor] An expiry racing with a user re-enable detaches the new session's probes
- Where: app/src/main/java/com/kino/puber/core/telemetry/TelemetryRuntime.kt:88-108; TelemetrySink.kt `expire()`
- Problem: `expire()` sets `isEnabled = false` and then does file I/O before it calls `onExpired()`. If `setEnabled(true)` runs inside that window, it finds `sink.isEnabled == false` and plants the probes again (it posts `attach`). The late `onExpired` then removes the pref key, uproots the tree, nulls `Telemetry.screen` and posts `detach` after `attach`. The sink keeps recording, but the frame, key and memory probes are detached and the switch time is lost. The tree, handler and pref part of this race predates the diff. This diff adds the probes and `screen` to what it tears down.
- Failure scenario: the user turns the log back on exactly as the seven-day expiry fires. The status shows Recording, but no `frames` or `mem` lines are ever written, and the next cold start finds no `enabled_at` key.
- Fix: tag each session with a generation counter. `onExpired` and `onStopped` should act only when the generation they were created for is still current.
