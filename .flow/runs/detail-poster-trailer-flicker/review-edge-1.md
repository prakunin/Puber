### F1 [minor] A failed details request leaves the previous card's poster on screen for good
- Where: /home/user1/orca/workspaces/Puber/detail-poster-trailer-flicker/app/src/main/java/com/kino/puber/core/ui/uikit/component/details/VideoItemGridDetails.kt:668-680 (`heldPosterUrls` / `rememberHeldUrls`). The producers are /home/user1/orca/workspaces/Puber/detail-poster-trailer-flicker/app/src/main/java/com/kino/puber/ui/feature/contentlist/vm/ContentListVM.kt:71-73 and /home/user1/orca/workspaces/Puber/detail-poster-trailer-flicker/app/src/main/java/com/kino/puber/ui/feature/favorites/vm/FavoriteVM.kt:108-117.
- Problem: The poster list is held while `isLoading && imageUrls.isEmpty()`, and nothing limits how long that lasts. Both VMs publish `VideoDetailsUIState.Loading` and then call `interactor.getItemDetails(id)` inside `launch`. If that call throws, `PuberVM`'s `DefaultExceptionHandler` catches it and `selectedItem` stays `Loading`. Nothing clears the hold until another card is focused and loads.
- Failure scenario: The network drops or the details request fails. The user moves from card A to card B in the catalogue or favourites. `Loading` is published, then the request fails. The panel keeps A's poster next to B's skeleton title and description for as long as focus stays on B. On base the panel showed a skeleton, which was stuck too but did not show another title's artwork.
- Fix: Release the hold once the request has failed. The smallest way: have the VMs publish a non-loading state on failure (catch around `getItemDetails` and set `selectedItem = Loading.copy(isLoading = false)` or an error state). Then `heldPosterUrls` returns the empty list and the panel falls back to the outer `request == null` skeleton.
