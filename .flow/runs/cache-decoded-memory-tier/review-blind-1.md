### F1 [minor] The memory cap is now counted in characters per feed rather than bytes for the whole cache, so the content memory tier can hold several times what it held before
- Where: /home/user1/orca/workspaces/Puber/cache-decoded-memory-tier/app/src/main/java/com/kino/puber/data/cache/ContentCacheRepository.kt:355-370 (`newFeed`, `MEMORY_TIER_ENCODED_CHARS`)
- Problem: The base had one `CachedFeed` with a cap of `16L * 1024 * 1024` weighed as `payload.length * Char.SIZE_BYTES`. That allowed 8M characters of JSON in total. The new code keeps the number 16Mi but weighs entries in encoded characters (`memoryWeigher = { encodedLength -> encodedLength }`), and gives that cap to each feed separately: `itemFeed`, `listFeed`, `pageFeed`, `historyFeed`, and one feed per payload key in `payloadFeeds`. The tier also now holds decoded object graphs (Item with its seasons, episodes and files trees), and nothing weighs their heap size; only the length of the JSON they came from is counted. The code comment says the cap "keeps the cap proportional", but against the old limit the item tier alone has doubled, and the per-feed caps add up.
- Failure scenario: A user opens the details of about 10 to 16 long series in one session (the code's own comment puts a long series at about 1 MB of JSON). The base would have started evicting at about 8M characters. Now `itemFeed` keeps all of them decoded, up to 16M characters, and the list, page, history and payload feeds can each keep their own share on top. On a low-RAM Android TV that is tens of MB more resident heap than before the change.
- Fix: If doubling the item tier was not intended, set the cap to 8M characters (`8L * 1024 * 1024`). If it was intended, say so in the comment. Either way, give the record-type feeds one shared budget (for example a single cap divided among them), or state the per-feed total explicitly.
