### F1 [minor] A pending entry restore is never retried when the rail closes, so the next handoff lands on the first card
- Where: app/src/main/java/com/kino/puber/ui/feature/showall/content/ShowAllScreenContent.kt:166, :209-213, :219
- Problem: `reconcile()` only runs from `LaunchedEffect(items)`. If `contentFocusActive()` is false when the entry loop starts, the loop returns false on its first attempt. C is skipped as well (correct), and `pendingEntry` stays true. When `LocalContentFocusActive` later turns true (the rail goes to HandingOff or Closed), nothing restarts `reconcile()`, because `contentFocusActive` is not an effect key. The drawer's `ContentFocusHandoffEffect` waits its 5 grace frames, "for a screen that remembers where the user was" (ContentFocusHandoff.kt:36-44), and then sends a blind request through the Main content box's `focusRestorer`. That request lands on whatever card a focus search finds first. `onCardFocused` then overwrites `lastFocusedId`/`lastFocusedIndex`, and `onGridFocusChanged(true)` clears `pendingEntry`, so the opener is gone for good.
- Failure scenario: The user opens the rail over Show all with focus on card 40, and the process is killed in the background. `rememberDrawerState` is saveable (ModalNavigationDrawer.kt:184), so the activity comes back with the rail Open, and the saved `lastFocusedId` makes `pendingEntry` true. `reconcile()` runs once while the content is inactive and does nothing. The user then presses Back or picks the same tab: the handoff starts, `contentFocusActive` turns true, and no restore runs. Focus lands on the first card that is composed instead of card 40. The base code has the same gap, but `pendingEntry` was added for exactly this "entry not yet landed" state, and it only covers the case where the rail was closed when the screen was entered.
- Fix: Key the effect on activity too, e.g. `LaunchedEffect(items, contentFocusActive) { memory.reconcile() }`. A flip to inactive just ends the run early, as it does now; a flip to active re-runs it, which only does anything while `pendingEntry` is set or the focused card has left. This stays inside the 5-frame handoff grace, keeps AC-6 (pending is already cleared once the grid holds focus), and does not steal from the rail, because the rail being open means inactive.

### F2 [minor] A reload after a foreign focus landing cancels the entry loop and drops the opener restore
- Where: app/src/main/java/com/kino/puber/ui/feature/showall/content/ShowAllScreenContent.kt:166, :198-200, :209
- Problem: At base, `restoreOnEntry` ran in `LaunchedEffect(Unit)`, so a list change could not cancel it. It kept asking for the opener even after something else had put focus in the grid. Now every `items` change cancels the running loop, and the restart only acts if `pendingEntry` is still true. Any grid focus clears that flag, including a landing the restore did not make. That landing also overwrites `lastFocusedId`/`lastFocusedIndex` through `onCardFocused`. So when a foreign landing and a list change both fall inside the restore window, the opener is not restored, even though it is still in the list.
- Failure scenario: The user re-enters through a tab switch (handoff with `expectsNewContent`), and a `Refreshing`→`Data` reload (for example `onReturnedContentChanges` or `displaySettingsChanges`) restarts the loop near frame 3. At frame 5 the handoff's blind request lands on card 1, which sets `lastFocusedId` to 1 and clears `pendingEntry`. A second list change (the `Data` that follows `Refreshing`, or a `LoadMore` append) cancels the loop that was still targeting the opener. `reconcile()` sees `pendingEntry=false` and the focused card still present, and returns. Focus stays on card 1. The same happens if the user presses D-pad inside the window. This is a narrow timing window, but base handled it.
- Fix: Let the loop that is already running finish, rather than gating it on the current flag. For example, clear `pendingEntry` only when the focused card is the one `restoreId` targets or when C fires, and leave it set on other landings until the in-flight loop ends. The alternative is to snapshot `pendingEntry` together with the saved id when the loop starts, and not let `onCardFocused` overwrite the saved id while an entry restore is still running.

No other boundaries survived checking:
- **Empty list:** the `Content` state never has an empty list, and `restoreId == null` skips both the loop and C.
- **Shrinking re-page and process death:** the restore index is clamped and the grid scroll is clamped the same way, so the target card stays visible.
- **Appends and remaps after landing:** both return early (AC-6).
- **C stealing focus:** C is gated on `pendingEntry` and `contentFocusActive()`, and Show all has no other focusable node while the entry is pending.
- **`LoadingNext` emitting an equal list:** the effect does not restart.
- **Recomposition cost:** writing an equal `restoreId` does not invalidate.
