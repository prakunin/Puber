### F1 [minor] On HLS, a broken side-loaded subtitle now stops video playback and switches the video URL
- Where: app/src/main/java/com/kino/puber/ui/feature/player/vm/PlaybackController.kt:436, :507 (`mediaItemFactory.build` + `player.setMediaItem`), and `streamRecovery()` at :333
- Problem: Before this change, HLS went through `HlsMediaSource.Factory` directly, which ignores `subtitleConfigurations`, so API subtitles were never loaded on HLS. Now every stream goes through `DefaultMediaSourceFactory`. That wraps HLS in a `MergingMediaSource` with one child per API subtitle. When a selected side-loaded child fails to load, Media3 raises it as a fatal player error. `onPlayerError` handles it like any stream failure: `streamRecovery()` maps 404/5xx/`ParserException` to `NEXT_URL` and 401/403 to `REFRESH_LINKS`. The diff does not mention this change.
- Failure scenario: The merger keeps a side-loaded row because the language is missing from the manifest, or the API has more files for it. The API URL for that file returns 404, or the file is malformed (`subtitleMimeType` falls back to SubRip for unknown extensions, so a misnamed file fails to parse). The viewer selects the row. After the retries, the player error moves playback to the next video candidate, which carries the same subtitle and fails again. Playback ends in an error screen, when the subtitle should simply have failed.
- Fix: Keep subtitle load failures away from the video recovery path. Either build the side-load children yourself with `SingleSampleMediaSource.Factory(...).setTreatLoadErrorsAsEndOfStream(true)`, or in `onPlayerError` detect a failing load whose URI is a side-loaded subtitle and turn text off instead of calling `onStreamFailure`.

### F2 [minor] The API `forced` value overrides the player's forced flag, so the selector can reject the exact track
- Where: app/src/main/java/com/kino/puber/ui/feature/player/vm/SubtitleTrackMerger.kt:146 (`isForced = apiTrack.isForced ?: isForced`); app/src/main/java/com/kino/puber/ui/feature/player/vm/SubtitleTrackSelector.kt:56
- Problem: Enrichment replaces the player-derived `isForced` with the API value. `SubtitleTrackSelector.isSemanticallyCompatibleWith` then requires the candidate's forced flag (taken from `format.selectionFlags` in `toPlayerTextTracks`) to equal the row's `isForced`. When the API and the manifest disagree, the filter removes the very track the row was built from, before the id and identity rules run.
- Failure scenario: A manifest rendition with `FORCED=YES` is matched by file path to an API entry with `forced: false`. The row becomes `isForced=false` and the candidate stays `isForced=true`, so `select()` returns null. No override is set, only `setPreferredTextLanguage` applies, and the player may show another track of that language or none.
- Fix: Keep the player's forced flag on player-backed rows (`isForced = isForced ?: apiTrack.isForced`). Alternatively, skip the forced check when the candidate matches by `playerTrackId`, group id or track index.

### F3 [minor] The same-language dedupe compares only counts, so a different subtitle can disappear from the picker
- Where: app/src/main/java/com/kino/puber/ui/feature/player/vm/SubtitleTrackMerger.kt:38-45
- Problem: For each language the merger keeps either all manifest tracks or all side-loaded tracks, chosen only by how many there are (manifest wins ties). It never checks whether the two sets hold the same subtitles.
- Failure scenario: The manifest has one `eng` rendition that is forced or partial. The API has one full `eng` file. It is a tie, so the manifest wins and the full English subtitle is no longer offered on HLS, though it was offered before. The same happens with 2 manifest vs 2 API tracks that only partly overlap.
- Fix: Drop a side-loaded track only when its source identity (or language plus forced flag) matches a kept manifest track, the way `selectTracksWithoutLanguage` already does for rows without a language. Keep the rest.
