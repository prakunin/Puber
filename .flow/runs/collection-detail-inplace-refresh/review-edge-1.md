### F1 [minor] A pending focus request in a non-target row never clears, and it keeps the requester on a card the user has left
- Where: /home/user1/orca/workspaces/Puber/collection-detail-inplace-refresh/app/src/main/java/com/kino/puber/core/ui/uikit/component/moviesList/FocusTargetState.kt:81-83 (with :241-248)
- Problem: The new `requestTargetId` uses `pendingFocus.itemId` whenever that card is still in `items`. Only the effect at :241 clears `pendingFocus`, and only when `isTargetRow` is true. Its keys are `pendingFocus.value, contentFocusActive`, without `isTargetRow`. Suppose a row's list changes while that row is not the target, and the card it remembered is removed. `ReconcilePublishedItemsEffect` then sets a pending request for the neighbour, and nothing clears it for the life of that composition. Later the user moves focus inside the row, which updates `focusedItemId`, but the `focusRequester` stays on the stale neighbour. Before this diff the requester followed `targetItemId`, which is resolved from `focusedItemId`, so this did not happen.
- Failure scenario: Home has rows A and B, and the user is in row A. Row B remembers card k > 0. After a return to Home, the refresh arrives after composition and removes that card from row B, so a pending request for the new card at index k is set and stays. The user goes Down into row B, then Left to the first card F, then Left once more to open the drawer. When the drawer closes, `contentFocusActive` goes from false to true and the pending effect runs `requestUntilFocused` on the requester, which still sits on index k. Focus jumps to index k instead of F. The tab re-entry effect (:288) and the anchor-restore effect (:249) hit the same stale requester. This affects every screen that uses the shared helper with more than one row (Home, SectionRow, VideoGrid rows). CollectionDetail and Bookmarks are not affected because there `isTargetRow` is always true.
- Fix: Let the pending id win only while it is still the current focus: `pendingFocus.value.itemId?.takeIf { id -> id == focusedItemId.value && items.any { it.id == id } } ?: targetItemId`. Another way is to clear `pendingFocus` when `isTargetRow` is false. Either keeps the AC-7 path, because there `focusedItemId` equals the pending id until the request lands.
