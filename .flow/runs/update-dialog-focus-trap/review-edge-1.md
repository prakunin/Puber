### F1 [major] The gate does not cover cold starts that open Details or the Player from a content link
- Where: app/src/main/java/com/kino/puber/ui/feature/details/component/DetailsScreenContent.kt:393-396; app/src/main/java/com/kino/puber/ui/feature/player/component/PlayerScreenContent.kt:83-97 and ResumeDialog.kt:51-52; the gate itself is at app/src/main/java/com/kino/puber/core/ui/navigation/component/FlowComponent.kt:159
- Problem: `ContentFocusGate` only works on code that reads `LocalContentFocusActive` or `LocalAutoFocusOnLaunchEnabled`. Details' first-button claim (`LaunchedEffect(state.trailerUrl, state.buttons.size)`) ignores both. So do the Player's controls focus, the resume-dialog focus and the error-overlay focus. These screens sit under the root gate when the app is launched with a content target: `LauncherVM.openStartScreen` calls `newRootScreens(main, target.toScreen(...))`, and `ContentTargetScreenMapper` maps targets to `details` or `player`. That is the same launch race as AC-1, with a different screen on top. Nothing in the diff stops these requests, and D6 has no re-claim. The spec names this as R1 but checks it only through Main/Home (M1).
- Failure scenario: cold start from a launcher channel or a content link to a series. The update check answers within the Launcher's 500 ms, so the prompt shows and focuses Update. Details then publishes its content and its `ActionRow` effect calls `firstButtonFocusRequester.requestFocus()`. Focus lands on Play under the scrim, and the trap no longer helps because focus is outside the overlay. The user can press Play beneath the prompt, which is the same symptom this run fixes. A Playback target is similar: the Player's controls or resume dialog take focus while the prompt is up.
- Fix: in the Details `ActionRow` effect, read `LocalContentFocusActive.current`, add it to the effect keys and return early when it is false. Do the same for the Player's launch claims (`PlayerScreenContent.kt:83`, `:94`, `ResumeDialog.kt:51`). At minimum, add a content-link launch to M1 so R1 gets evidence.

### F2 [minor] While Downloading (and Checking), nothing in the prompt can hold focus, so neither the trap nor the gate keeps the user in the dialog
- Where: app/src/main/java/com/kino/puber/ui/feature/update/component/UpdatePromptOverlay.kt:211 (`DownloadingContent`), :58-68
- Problem: pressing Update switches the state to `Downloading`, which removes the focused Update button. `DownloadingContent` has no focusable node, so focus leaves the overlay. The gate stays closed and the drawer stays in `HandingOff` (from `MainScreenComponent.kt:108`), so a bounce into the rail is sent on to the content (`redirectFocusToContent`). The retry loop runs again on every progress tick and fails every time, because `primaryFocusRequester` is not attached. The `onExit` trap only acts while focus is inside the group, and here it is not.
- Failure scenario: a real update is available and the user presses Update. On the next D-pad press focus enters Home under the scrim, Home scrolls (against AC-5), and Center on a card sends `ItemSelected` and opens Details under the progress dialog. The `Checking` state of the manual check behaves the same way. Q4 accepted that for Checking, but not for Downloading.
- Fix: give `DownloadingContent` a focusable node that `primaryFocusRequester` points to (for example a Cancel button that sends `DismissClicked`). Alternatively, make the overlay's card focusable when the state has no button.
