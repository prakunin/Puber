### F1 [minor] Every cache miss now runs a DELETE, so a read that finds nothing becomes a database write
- Where: /home/dev/orca/workspaces/Puber/cached-payload-row-too-big/app/src/main/java/com/kino/puber/data/repository/PersistentPayloadStore.kt:62-80 (`read`, `readAll`)
- Problem: `read` calls `dao.deleteOversized(listOf(key), …)` whenever no row comes back. `readAll` does the same for every key it did not find. Almost every miss is just a key that was never stored, but each one still runs a DELETE. That takes Room's single writer connection. The read path used to need only a reader, and now it waits behind any `upsertAll` that is running.
- Failure scenario: a cold start after the sweeper ran, or a first launch. `CachedFeed.peekAll` (CachedFeed.kt:360) and `peek` → `readUsable` (CachedFeed.kt:614) miss on most keys for every home shelf and details lookup. Each miss becomes a write transaction that matches nothing, queued behind the bulk item writes that `load`/`putAll` start at the same moment. Shelves that should open straight from cache wait on the writer, which hurts most on the TV box's slow flash. Rows are never wrong; only time is lost.
- Fix: delete only when an oversized row exists. Before the DELETE, run a select that reads no payload, such as `SELECT key FROM cached_payload WHERE key IN (:keys) AND length(CAST(payload AS BLOB)) > :maxBytes`, and call `deleteOversized` only on the keys it returns. Today's misses then stay on the read connection. Alternatively, accept the cost and record it in the spec's Risks table, which today lists only the hit path (R8).

### Unproven
- PersistentPayloadStore.kt:63 A read now writes. If the database is full or read-only, `deleteOversized` throws (for example `SQLiteFullException`), so a read that used to return null now fails. This becomes real only with evidence that the box ran out of storage or that the database was opened read-only.
- PersistentPayloadStore.kt:167 `utf8Size` counts a lone surrogate as 3 bytes. Kotlin's `encodeToByteArray` (used only in the log line) and SQLite's UTF-16→UTF-8 conversion may count it differently, so the write check and the SQL predicate could disagree near the limit. This becomes real only with a server payload that holds unpaired surrogates and is within a few bytes of 1 MiB.
- CachedPayloadDao.kt:14-20 `CAST(payload AS BLOB)` measures bytes in the database's text encoding. If `puber.db` were UTF-16, rows between 0.5 and 1 MiB would be deleted on every read. This becomes real only if `PRAGMA encoding` on the box is not UTF-8. `PersistentPayloadStoreDbTest.aMultiByteRowJustUnderTheLimitRoundTrips` would catch it once run on the box.
