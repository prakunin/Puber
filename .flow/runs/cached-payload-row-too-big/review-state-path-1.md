### F1 [minor] A refused write deletes another writer's row by key, unconditionally
- Where: app/src/main/java/com/kino/puber/data/repository/PersistentPayloadStore.kt:115-118 (refuse → dao.delete(key)), reached from CachedFeed.load at app/src/main/java/com/kino/puber/data/cache/CachedFeed.kt:239-266.
- Problem: refuse runs inside store.write, after CachedFeed has already done its epoch check. Its dao.delete(key) has no ownership condition. CachedFeed guards every other delete so that it only removes the writer's own row (supersedesWrite, and the comment in putAll "a delete would leave every list naming this key pointing at nothing"). The refused write skips that rule. It also leaves the delete on the data path before the epoch can be checked again: refuse encodes the whole payload with encodeToByteArray() only to log its size, which allocates several MB.
- Failure scenario: a details load for a long series X is running (for example a DetailsPrefetcher warm on the focused 4K card). At the same moment another section's page that contains X merges its cards (mergeItems → itemFeed.putAll). The details write ends up deleting the fresh card row, and then the details load drops its own value from memory. X is then in neither tier. The page just loaded emits without X's card, and the gap stays for this session until the next forced refetch of that list (or permanently while offline).
- Trace:
  1. Details load(X): the loader returns the big record, settled == epoch passes, store.write(X, big) is called. Inside it, isOversized is true, then refuse spends time on encodeToByteArray before dao.delete(X).
  2. In that window, list putAll: advanceKey(X) (an ordinary write, not supersede), then writeAll upserts the small card row X. Then settled == epoch → memory.put(X, card).
  3. refuse's dao.delete(X) lands and removes the row from step 2.
  4. Back in load: settledAfterWrite != epoch, so discardValue is set (no store.remove, because supersedesWrite is false). loadFresh returns, then detachSupersededValue(X) → memory.remove(X), which drops the card value from step 2.
  5. observeItemPage collects the page, readItems(ids) → peekAll misses X in memory, and readAll has no row for it. The card is dropped from the emitted page.
- Fix: keep the store from deleting by key. Have write / writeAll report the keys they refused (or expose a delete-if-owned hook), and let CachedFeed remove the row only when it still owns the key: in load, epochOf(key) == epoch right after the write; in putAll, settled == epoch. Supersede writes (markItemDetailsStale / invalidateItemDetails) keep the delete, because they own the key by construction. Compute the logged byte count without encodeToByteArray (the utf8Size bound is enough).

### F2 [minor] The spec's mitigation "the next list merge writes a small record again" does not hold while the big record is in memory
- Where: app/src/main/java/com/kino/puber/data/cache/ContentCacheRepository.kt:327-347 (mergeItems reads existing from the memory tier); the claim is in the spec, docs/superpowers/specs/2026-11-24-cached-payload-row-too-big.md:108.
- Problem: once X's details record is over the limit, every later card merge for X starts from the in-memory details record. The merged record is still over the limit, so it is refused again and the card row is deleted again. X's card is never persisted while that record lives in memory. When the weight cap (MEMORY_TIER_ENCODED_CHARS) evicts it, and these are the heaviest entries, the card is in neither tier for the rest of the session. After any process death, every list or page naming X is force-refetched by queryNeedsRefetch. While offline, readItems drops X's card and the refetch fails as RefreshFailed, so the card stays missing.
- Failure scenario: open the details of a long 4K series, then go back to the 4K «Все» grid and scroll through pages that contain it. Every merge refuses X and deletes its card row. Restart the app offline (or have memory evict X): the «Все» page shows without X's card.
- Trace:
  1. observeItemDetails(X) → mergeItemRecord(details = true) builds a record over 1 MiB → store.write refused → dao.delete(X); memory holds the details record.
  2. Page load → mergeItems(details = false) → readItemRecords returns the big record from memory → mergeItemRecord keeps seasons / videos (mergeSparse keeps them when incoming is null) → putAll → writeAll refused → dao.delete(X).
  3. Eviction or cold start: peekAll(X) finds nothing → readItems drops X, queryNeedsRefetch is true and forces a refetch.
- Fix: when the merged item record is over the limit, persist a card-only copy (the record with seasons / videos cleared and detailsUpdatedAt = null) and keep the full record in memory only. That fits Q2 ("memory only" for details), and cards then really stay cached. At minimum, correct the risk row so it describes this behaviour (the card stays unpersisted for as long as the details record is in memory).
