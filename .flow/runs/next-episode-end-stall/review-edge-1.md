### F1 [minor] The new end-of-episode switch releases ExoPlayer from inside ExoPlayer's own state callback
- Where: /home/user1/orca/workspaces/Puber/next-episode-end-stall/app/src/main/java/com/kino/puber/ui/feature/player/vm/PlayerVM.kt:1407 (`countdownDismissed -> playNextEpisodeOrShowEndedControls()`), reached from /home/user1/orca/workspaces/Puber/next-episode-end-stall/app/src/main/java/com/kino/puber/ui/feature/player/vm/PlaybackController.kt:231-234
- Problem: `PlaybackController.playerListener.onPlaybackStateChanged(STATE_ENDED)` calls `callback?.onPlaybackEnded()`. That call goes straight into `PlayerVM.onPlaybackEnded()`, with no `launch` and no post in between. On the new dismissed path, `onPlaybackEnded()` runs `playNextEpisode()`, then `switchEpisode()`, then `playbackController.release()`. `release()` calls `removeListener` and `player.release()` on the same ExoPlayer that is still dispatching this event.
  - The same file says this is not allowed (PlaybackController.kt:686: "Releasing from inside a player callback is not allowed; hand it to the loop"). The warm-up player follows that rule by posting the release.
  - Before this change, nothing on the ended path released the player synchronously: the countdown switched after a coroutine `delay`, and `exitPlayer()` only pauses.
  - Any other listener on that player (the PlayerView component listener, the analytics side) is either skipped for this event or gets it from a released player.
- Failure scenario: a viewer cancels the prompt, the episode ends with no panel open, and the player is released and rebuilt in the middle of ExoPlayer's listener dispatch. Device run M2 passed once without a crash, so this does not fail every time. It does break the project's own documented constraint, and depending on the Media3 version or on which listeners are attached, it could crash or leave a stale surface.
- Fix: defer the switch out of the callback, for example `launch { playNextEpisodeOrShowEndedControls() }`, or post it the way `releaseWarmUpPlayer` does. Do the same for the switch triggered by `advanceWhenPanelCloses` only if `onPanelClosed` can run from a player callback (today it runs from user input or the hide timer, so it does not need it).
