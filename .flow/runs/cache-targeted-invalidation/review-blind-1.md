### F1 [minor] Stale mark and Home refresh are lost if the player is torn down before the background flush finishes
- Where: app/src/main/java/com/kino/puber/ui/feature/player/vm/PlayerVM.kt:1498-1504 (`pauseForBackground`), :1974-1982 (`flushOwedInvalidation`), :2035 (`onCleared`)
- Problem: Before this change, each successful `saveWatchingTime` marked the details entry stale right away. Now the change is only recorded as `detailsStaleOwed` / `homeRefreshOwed` and acted on later, in a `viewModelScope` job. On background, that job first waits for `awaitPendingMutations()`. The wait includes the network save that `saveCurrentPosition()` starts on ON_STOP. If the ViewModel is cleared during that wait, the scope is cancelled and the owed work is dropped. `onCleared` does not flush it either. So the periodic saves that already succeeded, possibly minutes of them, are never announced. Under the old code those saves had already marked the entry stale.
- Failure scenario: The user watches for 10 minutes, so the 30 s tracker saves succeed and set the flags. The user presses Home, which fires ON_STOP and starts the final save over a slow network. The user then picks the same title from the launcher row. `MainActivity.onNewIntent`, then `WarmContentLaunchHandler`, then `router.newRootScreens(...)` replace the stack and clear the player VM. The flush job is cancelled before `markItemDetailsStale` and `requestRefresh` run. The newly opened Details or Player reads a details entry that still counts as fresh and shows the position from before the session. The TV Home row is not refreshed either.
- Fix: Run the flush where cancelling the VM cannot stop it. One way: put the work after `awaitPendingMutations` in an application-scoped or `NonCancellable` context. Another: record the owed stale mark as soon as the first successful save happens, so it does not depend on the flush. Flushing synchronously from `onCleared` through an app scope also works.
