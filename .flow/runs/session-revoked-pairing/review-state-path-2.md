### F1 [minor] Claiming the end before its clears finish can skip the clears for good
- Where: /home/dev/orca/workspaces/Puber/session-revoked-pairing/app/src/main/java/com/kino/puber/ui/feature/root/component/App.kt:99-111 and /home/dev/orca/workspaces/Puber/session-revoked-pairing/app/src/main/java/com/kino/puber/core/session/SessionEventBus.kt:37
- Problem: `claimPendingEnd()` marks the end as handled before any clear has run. Several of the clears suspend (`clearAccountPrograms`, `watchStateSyncInteractor.invalidate`, `contentCache.clear`, `detailsPrefetcher.invalidate`). `clearWithoutFailing` passes cancellation on, so if the `LaunchedEffect` is cancelled partway through, the rest of the clears never run. The end stays marked as handled. The next handler only replays it and routes, so nothing ever runs those clears again. Before this round, the replay re-ran every clear, which covered this case.
- Failure scenario: a 403 `user_banned` or a failed refresh happens while the user is on Main. The handler claims the end, runs `clearSession()`, and suspends in `contentCache.clear()`. The user presses Back on the root Main screen, which finishes the Activity and disposes the composition, so the coroutine is cancelled. `contentCache.clear` is cut short and `detailsPrefetcher.invalidate` never runs. The user relaunches. The new handler gets `claimPendingEnd()` = false, so it only routes to `auth(reason)`. The previous account's cached feed and prefetched details survive the end. The next account paired on the device can see them until they are refetched.
- Trace: `emit(Pending1)` -> handler: `claimPendingEnd()` sets `claimed=true` -> `clearSession()` -> `clearAccountPrograms()` -> `invalidate()` -> `contentCache.clear()` suspends -> Activity destroyed, `CancellationException` -> new Activity, handler: `claimPendingEnd()` returns false (Pending1 still pending, `claimed=true`) -> `newRootScreen(auth)` only, with no clears.
- Fix: release the claim if the clears do not complete, or set it only after they finish. For example, wrap the clears in `try { … } catch (c: CancellationException) { sessionEventBus.releaseClaim(); throw c }`, where `releaseClaim` resets `claimed` on the same `Pending`. A replay that finds the end unclaimed then runs the clears again. Note that `contentLaunchCoordinator.clearSession()` runs first and does not suspend, so the round-1 deep-link fix (F4) still holds after a release. Add a bus test: claim, release, then a second claim returns true.
