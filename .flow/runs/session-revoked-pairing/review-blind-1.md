### F1 [minor] The pairing screen's own requests refill the bearer cache with empty tokens, so clearing it at session end does not take effect
- Where: /home/dev/orca/workspaces/Puber/session-revoked-pairing/app/src/main/java/com/kino/puber/data/api/KinoPubApiClient.kt:274 (with `loadTokens` at :152-155 and `shouldSendKinoPubToken` at :1245)
- Problem: `onSessionExpired` calls `httpClient.clearAuthTokens()` so that a new pairing sends the new token. But Auth's device-code and poll requests go through the same `httpClient` to `OAUTH_BASE_URL`, and `shouldSendKinoPubToken` returns true for that host. So `sendWithoutRequest` loads tokens again while the prefs are empty. Ktor then caches `BearerTokens("", "")`. When pairing succeeds, `KinoPubRepository.getAuthState` saves the tokens to prefs only and never clears Ktor's cache. The first content request after pairing therefore sends `Bearer ` with no token, gets a 401, and triggers a refresh. The test `aRepairAfterTheSessionEndedSendsTheNewToken` does not catch this because it makes no request between the end and `prefs.set(...)`.
- Failure scenario: The session ends, Auth fetches a device code (the empty pair is cached), and the user pairs. Home's first request gets a 401 and a refresh runs with the new refresh token. Every re-pairing costs an extra refresh and a token rotation. If that refresh fails on the network, the `catch (e: Exception)` branch calls `sessionExpiredFailure` with `presentedToken = null`. The new tokens are stored, so the check passes and the brand-new session ends, sending the user back to Auth.
- Fix: Call `httpClient.clearAuthTokens()` after the pairing tokens are saved, through a client method that the repository calls on success. Or make `loadTokens` return `null` when no access token is stored, so no empty pair is cached or sent. Then extend the re-pair test with a `getDeviceCode()` call before `prefs.set`.

### F2 [minor] Any 403 is now treated as an account refusal in the UI, though the API layer keeps the session for unlisted 403s
- Where: /home/dev/orca/workspaces/Puber/session-revoked-pairing/app/src/main/java/com/kino/puber/ui/feature/home/vm/HomeVM.kt:436, :185; /home/dev/orca/workspaces/Puber/session-revoked-pairing/app/src/main/java/com/kino/puber/ui/feature/device/settings/vm/DeviceSettingsVM.kt:204, :267
- Problem: `httpFailure` maps every 401 and 403 to `ApiError.Unauthorized`. Only a 401 or a 403 `user_banned` ends the session; the test `anUnlistedForbiddenAnswerKeepsTheSession` confirms that an unlisted 403 keeps it. The new UI checks key on `ApiError.Unauthorized` / `CODE_UNAUTHORIZED`, so they treat an unlisted 403 like a refused session. DeviceSettingsVM now rethrows `Unauthorized` itself instead of wrapping it in `IllegalStateException`, so its message changes to `error_unauthorized` ("The session has expired. Sign in again.").
- Failure scenario: A mirror or custom domain answers 403 with any other body, for example a CDN or nginx deny page, on every Home section. Home shows the error view with only Retry: the mirror action, the one way out, is hidden. No session end follows, so nothing routes to Auth. Settings in the same state says the session expired while the tokens are still valid.
- Fix: Decide on the session-ending condition (`sessionEndReasonFor != null`), not on the error type. For example, have the client mark ApiError with a flag or subtype when it ended the session, and hide the mirror action and pick the message only in that case.
