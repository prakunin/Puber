### F1 [minor] The end is marked handled before its clears run, so a cancelled handler leaves the old account's data behind for good
- Where: /home/dev/orca/workspaces/Puber/session-revoked-pairing/app/src/main/java/com/kino/puber/ui/feature/root/component/App.kt:99-111 and /home/dev/orca/workspaces/Puber/session-revoked-pairing/app/src/main/java/com/kino/puber/core/session/SessionEventBus.kt:37
- Problem: `claimPendingEnd()` marks the end as handled before any clear runs. The clears that follow can suspend: `tvHomeSyncCoordinator.clearAccountPrograms()` waits on `reconciliationMutex` for as long as a TV-home reconcile is running, and `watchStateSyncInteractor.invalidate()` and `contentCache.clear()` are suspend calls too. `clearWithoutFailing` rethrows `CancellationException`. If the `LaunchedEffect` is cancelled partway, the clears not yet run are skipped. When the next handler replays the end, `claimPendingEnd()` returns false, so it only routes. Before this diff, the replay ran every clear again and so repaired this case. The fix for triage item 4 removed that.
- Failure scenario: an end (403 `user_banned`, or a failed refresh) arrives while a TV-home reconcile holds the mutex. The user presses Back on Main, which on TV finishes the Activity and disposes the composition. The handler is cancelled inside `clearAccountPrograms()`. The process stays alive, and on relaunch the new handler replays the end and goes straight to Auth. The watch-state index, the content cache and the details prefetch of the ended account are never cleared, and a different account paired next sees them.
- Fix: release the claim if the clears do not finish. For example, wrap the clears in `try { ... } catch (c: CancellationException) { sessionEventBus.releaseClaim(); throw c }`, where `releaseClaim` resets `claimed` on the current `Pending`. Another option is to mark the end claimed only after the last clear. Add a test: claim, cancel during a suspending clear, then replay and check that the clears run.
