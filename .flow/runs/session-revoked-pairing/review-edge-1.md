### F1 [minor] On cold start the Launcher can still open Main after the handler has already sent the user to Auth
- Where: app/src/main/java/com/kino/puber/ui/feature/root/vm/LauncherVM.kt:34-58, with app/src/main/java/com/kino/puber/data/api/KinoPubApiClient.kt:262-275
- Problem: `onSessionExpired` emits the end first and clears the tokens after it, inside `sessionLock`. `isAuthenticated()` is locked so it cannot read a token between the two, but `LauncherVM.onStart` skips that lock: it calls `cryptoPreferenceRepository.getAccessToken()` directly on IO. `hasPendingEnd` is checked only in the unauthenticated branch. So a Launcher that reads the token after the emit and before the clear goes to `main()`. Meanwhile the handler in App.kt was already resumed on Main by the emit, so its `newRootScreen(auth(reason))` can run first. The Launcher's `newRootScreen(main())` then replaces Auth.
- Failure scenario: this is the AC-8 cold start on the banned box. Warm-up (`AppStartup.warmUp`, IO) gets `403 user_banned` and emits Blocked. Before the clear finishes (Keystore-backed prefs writes), the Launcher reads the token. The handler re-roots to Auth, and the Launcher's continuation lands Home on top of it with no tokens. Home's requests now go out with an empty bearer, so `presented.isEmpty()` blocks any second end. The user is stuck on Home's error with Retry only (no mirror button, no route to Auth) until the next process start. The window is a few ms, but it opens on every launch of a banned session.
- Fix: in `openStartScreen`, return when `sessionEventBus.hasPendingEnd` before either branch. Or read the token through the locked `isAuthenticated()` (`authInteractor`) instead of the repository.

### F2 [minor] The blocked reason does not survive a process restart, so a relaunch shows plain pairing and invites re-pairing the banned account
- Where: app/src/main/java/com/kino/puber/core/session/SessionEventBus.kt:16-32; app/src/main/java/com/kino/puber/ui/feature/root/vm/LauncherVM.kt:55-59
- Problem: the reason lives only in the in-memory `pending` StateFlow and in the parcelled `AuthScreenParams`. After the process dies (user leaves the app and the TV box kills it, or a force-stop), the tokens are gone and the bus is empty. The Launcher then opens `auth()` with reason `null`, and the blocked line is gone.
- Failure scenario: this was observed on the box in round 1 (evidence `2026-11-26-session-revoked-pairing-device.md`, "Second launch ... Auth without the blocked line"). The r2 change (replay bus) does not cover it, because the replay is in memory only. The user sees an ordinary pairing code, pairs the banned account again, and gets ejected. That is the re-pair loop the spec's AC-6 text is meant to prevent.
- Fix: persist the last end reason (one preference written in `onSessionExpired`, cleared where `clearPendingEnd()` is called on pairing success). The Launcher passes it to `auth(reason)` when no token is stored.
